## Design spec for the computer-use fork

Documented the full design for bringing computer use to Hyprland agents. The spec covers agent screens (hidden, silent input and capture), control of the human's desktop (with accepted keyboard-focus blips), and a waybar menu to list agent screens. Success criteria include screen creation, Chrome automation via Chrome DevTools Protocol, recording to MP4, clipboard/file I/O, and desktop window control. Spike on 2026-09-29 confirmed that the base (hexadecimil/hyprcage fork) works on arjun-e16 with Chrome on an agent screen, screenshots under lock, and no disruption to the human's focus. Architecture divides into the fork itself (adds record/clipboard/file/browser/desktop tools in Go), Chrome control (reuses chrome-devtools-mcp with fixed `--browserUrl`), and a waybar module. Portability addressed by moving machine-specific config to `~/.config/hyprcage/config.toml` and teaching the installer both zypper and pacman. Testing plan includes upstream tests, go tests for each tool, smoke script on both machines, and browser E2E with DevTools MCP visible in the mirror. Status: design approved in conversation, waiting for spec review before implementation.

## Implementation plan

Wrote a 2680-line task breakdown for implementing the fork. Planning revealed five spec amendments: `wf-recorder` 0.6.0 breaks on openSUSE (libavformat symbol error), so both desktop and agent recording use `ffmpeg` piped from hyprcage's capture; `file_put`/`file_get` are dropped because agent screen applications already run as the human's user with file system access; no stand-alone Hyprland rules file is needed (hyprcage positions the mirror itself); clipboard works in cage with `wl-copy`/`wl-paste`; and `ffmpeg` encoders differ per distribution, so the encoder is chosen from a preference list. The plan spans 12 tasks: amend the spec, install external packages, configure recording and browser options, add Go packages for recording state management, clipboard operations, desktop window operations, Chrome control, and the MCP server handlers; write CLI twins and the waybar module; and run the smoke script. Each task has numbered steps with checkbox syntax for tracking.

## Recording frame loop and config

Implemented `internal/record/` to handle screen/desktop capture → ffmpeg pipeline. `Loop()` captures frames on schedule, writes raw RGBA to ffmpeg's stdin, and handles timing drift by repeating the previous frame if capture falls behind. Encoder selection (libx264, libopenh264, fallback mpeg4) handles distro differences; scale filter rounds dimensions to even numbers for yuv420p. Added config fields for recording directory (`~/Videos/agent`), max duration (30m default), fps (10 default), and browser settings (Chrome binary, DevTools port 9222). Config parsing reads toml `[record]` and `[browser]` sections with validation (fps ∈ [1,60], port ∈ [1024,65535], max ≥ 1s). Helpers: `ExpandHome()` substitutes `~/` with home directory, `FFmpegArgs()` builds the command line. Tests cover config defaults, overrides, validation boundaries, and frame expansion. Ready for integration with screen capture once wl.Client is available.

## Recording state and MCP integration

Completed the recording control plane: `internal/record/state.go` and `state_test.go` track live recorder PIDs in json files under the registry dir. `Start()` spawns the recording subprocess detached and waits for its state file to confirm startup. `Stop()` sends SIGTERM to the PID and returns the MP4 path (file size included if available). `Load()` and `List()` validate PIDs with `syscall.Kill(pid, 0)` (lightweight check, no signal sent) and clean up stale state files automatically. Integrated into the MCP server as `record_start` and `record_stop` tools in `server_fork.go`; `record_start` dispatches to the running binary with `_record target out` arguments (the CLI wrapper runs the frame loop and manages ffmpeg). Desktop recording locked when session is locked via `lockedFn` callback (task 7 will wire it to `desktop.Locked()`). Live tested on arjun-e16 (Hyprland 0.56.2): 5 s kitty screen at 10 fps produced h264, 1280×800, 51 kB; desktop 3 s produced h264, 1920×1200, 31 kB. Bitrate measurably lower than intended (51 kB/5s vs ~300 kB/s at q=18), hypothesis: ffmpeg default crf is high (around 28), will tune in task 9.

## Desktop operations: list, focus, move, type, key

Implemented task 7: agent control of the human's windows through Hyprland IPC. Package `internal/desktop/` exposes five operations via CLI and MCP tools. `Windows()` lists all clients except hyprcage mirrors. `Focus()`, `Move()`, `Type()`, and `Key()` all validate input (strict address format `0x[0-9a-f]+`, checked rune-by-rune for type operations, key modifiers parsed from `ctrl+shift+...` syntax), check the desktop lock status via `Locked()` (reads `/proc/*/comm` for hyprlock), and bail if the desktop is locked. `Type()` maps each character through `KeyFor()` (hardcoded US layout with shifted pairs like `{` → SHIFT+bracketleft) and rejects unsupported runes with a clear error. `Key()` parses modifiers and key names, validates key names against `[A-Za-z0-9_]+`, and rejects bad modifiers; `ParseCombo()` is testable standalone. Input rejection is strict: a single unsupported character in a type operation aborts without sending anything, avoiding partial input. All operations use `send_shortcut` which Hyprland documents as "moves the focused window out of the way, sends the key to the target, and focuses back" — the human accepted this focus blip on 2026-09-29. Tests cover character mapping boundaries (a-z, A-Z, 0-9, symbols), combo parsing, address format, and lock detection. No tests yet for the e2e CLI or MCP integration; integrations (focus blip, Hyprland uptime) are live-tested only.
